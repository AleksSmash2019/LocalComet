## 1. Резюме для владельца (простым языком)

**Где LocalComet сейчас.** Ядро безопасности крепкое и по сравнению с опенсорсом — **сильнее среднего**: цепочка одобрений с одноразовыми токенами есть только у Goose, и у LocalComet она строже (уровни риска из проверяемого TOML-реестра, а не «мнение модели»); загрузка моделей с SHA-256 и пиннингом хоста — это урок Probllama (Ollama RCE через подделанный манифест), выученный заранее; локальный сервер без внешнего доступа — правильный дефолт, за который Ollama критикуют до сих пор.

**Куда расти (топ-5 по соотношению эффект/усилия):**

1. **Долгая память диалога** — модель видит 2 последних сообщения. Это главный «ощущаемый» потолок качества: любой длинный разговор теряет начало. (BUG-5, открыт)
2. **Жизнь после перезапуска** — вся история чатов и задач в оперативной памяти; рестарт приложения = потеря. Персистентный task_ledger уже написан, но не подключён к чату. (BUG-2)
3. **Очередь и автоповтор** — вторая задача получает мгновенный отказ «занято», ошибки с флагом «повторяемая» никем не повторяются автоматически. Это разница между «инструментом» и «помощником». (BUG-7/9, открыты)
4. **Дозагрузка моделей** — обрыв на 90% гигабайтной модели = качать с нуля. HTTP Range — дешёвое решение с большим эффектом. (открыто)
5. **Гигиена релиза** — CSP с dev-портами, fail-open в `allows_tool`, skills без таймаута: три мелочи, каждая на полчаса работы, вместе закрывают целый класс «а что если». (SEC-5/6, часть SEC-2)

**Главный вывод сравнения:** LocalComet не догоняет опенсорс — он в нём уже впереди по архитектуре безопасности. Отставание в другом: в «качестве жизни» (память, очереди, дозагрузка, долгие задачи), где LM Studio и Jan дали пользователям больше. Это и есть карта точек роста.

## 3. Сравнение с опенсорс-проектами

### Инциденты (чему их учат)

| Проект | Крупные инциденты | Урок для LocalComet |
|---|---|---|
| **Ollama** | CVE-2024-37032 «Probllama» (path traversal в манифесте → RCE, CVSS 8.8); CVE-2024-28224 (DNS rebinding к localhost:11434); 4 CVE из отчёта Oligo (краши на GGUF, утечки существования файлов); CVE-2025-63389 (нет аутентификации management-эндпоинтов, 9.3) | Валидировать сам формат манифеста/дайджеста (сделано: magic bytes GGUF + SHA-256 + пиннинг хоста); не открывать порты наружу (сделано: loopback-only) |
| **Open WebUI** | 14 страниц GitHub-адвайзори; хронический класс — SSRF (DNS rebinding в Playwright-лоадере, fetch по невалидированным редиректам), XSS→угон аккаунта, обход ACL | SSRF-защиты `_web_fetch` (scheme/port allowlist, DNS-pinning, без редиректов) — уже на уровне лучших практик; держать планку на всех новых сетевых путях |
| **Jan** | Публичных security-адвайзори нет вообще (это отсутствие записей, а не доказательство чистоты); креды недавно переехали в backend-хранилище | Прозрачность LocalComet (публичные аудиты, evidence-цепочка) — редкость в этой категории, ценить и продолжать |
| **LM Studio** (проприетарный, ориентир) | — | Их формула: loopback по умолчанию + opt-in наружу + рекомендация аутентификации в момент открытия. LocalComet-у из этого нужен только контроль «случайно не открыть наружу» — сейчас его и нет: у сервера вообще нет настройки бинда, что безопаснее, но при будущем «сервер для других приложений» формулу LM Studio взять за образец |
| **Goose** | — | Их Approve/Smart Approve с per-tool «Always allow / Ask before / Never allow» — принятый UX-паттерн approval-цепочек; слабость Goose — уровень риска определяет «мнение LLM». LocalComet строже: read_only/guarded/dangerous из TOML-реестра, проверяемого гейтами. Но у Goose есть то, чего нет — **режимы**: у LocalComet один жёсткий режим без «доверенного профиля» для длинных задач |
| **AnythingLLM** | — | RBAC-модель невеличка для десктопа, но их урок: пароль инстанса = полный контроль. У LocalComet одно-пользовательская модель — приемлемо |

### Сводка «кто где сильнее»

- **Безопасность по умолчанию:** LocalComet впереди поля (approval-цепочка + TOML-реестр + evidence). Ollama до сих пор без аутентификации API.
- **SSRF/сетевой периметр:** LocalComet на уровне лучших практик (Open WebUI — хроникёр этого класса).
- **Supply chain моделей:** LocalComet впереди (SHA-256 + magic bytes + https-pinning + TOCTOU-реверификация; Ollama заплатил за отсутствие RCE-инцидентом).
- **Стабильность модели и UX долгих задач:** отстаём от LM Studio (память диалога, дозагрузка, очередь) — детально в §4.
- **Agent-разрешения:** паритет с Goose по сути, преимущество в верифицируемости; отставание в режимах (unattended) и отмене tool.call.

## 4. Точки роста (полная карта, приоритизированная)

### A. Качество повседневной работы (самое ощутимое)

1. **P0 · Память диалога.** Поднять gateway-лимиты (4 msg / 16 КБ) до реалистичных (≥32 msg / ≥128 КБ) + компакция: суммаризация старых ходов, token-учёт. FE `slice(-2)` согласованно поднять. Без этого остальное улучшение UX почти не видно пользователю.
2. **P0 · Персистентность чатов.** chatMessages → localStorage/файл (через Rust-слой с безопасной записью), restore при старте. `task_ledger.rs` уже есть — подключить к чат-циклу (Фаза 1 DEEP_AUDIT).
3. **P1 · Range-догрузка скачиваний.** HTTP Range + append в .partial вместо create_new; конфликт-ошибку partial_name_conflict заменить на resume. Для 27B-моделей на домашнем интернете — критично.
4. **P1 · Очередь запросов.** Bounded queue в gateway вместо мгновенного `busy` + честный UI «в очереди». Одновременно решает и «двойной клик = отказ».
5. **P1 · Авто-ретрай retryable.** Один цикл с backoff (2 попытки) на retryable=True в Rust-реестре — флаги уже производятся, потребителя нет.

### B. Надёжность движка

6. **P1 · Фоновый сторож llama.cpp.** Авто-restart есть, но детект ленивый. Лёгкий poll-поток (1 Гц проверка process handle, restart через существующий путь status()) закрывает окно «упал — а UI узнает через минуту».
7. **P2 · Unattended-режим одобрений.** Очередь одобрений с длинным TTL + «deny-and-continue» для guarded-класса на выбор пользователя. Сейчас отсутствие человека на 3 минуты гарантированно убивает задачу. Это же — главный блокер для «оставил задачу и ушёл».
8. **P2 · tool.cancel.** Кооперативная отмена tool.call (контракт уже описан в IPC). Вместе с п.7 превращает агента из «одноразового» в управляемого.

### C. Гигиена релиза (быстрые победы, по полчаса каждая)

9. **P2 · SEC-5 CSP.** Разделить devCsp и релизный csp; убрать localhost:1420/1421 и data:/blob: из релиза. Один файл.
10. **P2 · SEC-6.** `_ => true` в allows_tool инвертировать в allowlist. Одна строка + тест.
11. **P2 · SEC-2 хвост.** Пин python.exe абсолютным путём + таймаут на skills-процесс. ~20 строк.
12. **P3 · SEC-4.** HKLM приоритетнее HKCU в App Paths резолве брокера + показывать резолвнутый путь на карте одобрения.

### D. Продуктовые направления (стратегические)

13. **Каталог моделей с проверками сообщества.** Сейчас approved-каталог зашит в бинарник. Рост: обновляемый каталог (подписанный) + статусы «проверено сообществом» — то, за что любят LM Studio/Ollama-реестры, но без их отсутствия верификации.
14. **Сервер-режим (позже).** Если появится «дать другим приложениям доступ к модели» — взять формулу LM Studio: loopback по умолчанию, opt-in наружу, аутентификация в момент opt-in, отдельный токен на приложение.
15. **Мультидвижок.** Runtime-neutral интерфейс из UP05-блюпринта: llama.cpp сегодня, но контракт уже позволяет добавить второй движок без переписывания approval-цепочки. Конкурентное преимущество на 2-3 года.

## 5. Новые поверхности, которых не было в прошлых аудитах

1. **Dev-стейджинг доверяет репозиторию целиком.** `launch_localcomet_dev.py` копирует исходники в %LOCALAPPDATA%\LocalCometDev\workspace, и vite оттуда их сервит. Проверки подлинности staged-корня есть (symlink/метаданные), но содержимое каждого файла не верифицируется — это осознанный dev-режим, стоит лишь задокументировать как «не для продакшена».
2. **`approval.no_pending`** — неиспользуемый ключ i18n после недавней правки ApprovalCard (космос, не риск).
3. **Апдейтер отсутствует.** Для будущего распространения: Tauri-updater с подписью minisign — обязательный стандарт (неподписанные обновления = главный вектор атак на десктопные приложения).
4. **web.search без лимита чтения** — подтвердил: `tool_execution_ru.py:793` всё ещё `resp.read()` без ограничения (SEC-8 из DEEP_AUDIT, открыто; контраст с _web_fetch 10 КБ).
