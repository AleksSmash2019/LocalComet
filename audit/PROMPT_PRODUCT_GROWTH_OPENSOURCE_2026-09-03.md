## 3.3. ФИКСИРОВАННЫЙ БЕНЧ-НАБОР (метрики §1.3 меряются только на нём, до/после)

S1 «двойная отправка»: два сообщения подряд во время генерации → оба обработаны, ни одного busy/потери.
S2 «длинный разговор»: 20+ сообщений, вопрос по началу диалога → ответ корректен без ручного копипаста.
S3 «многошаговый код»: задача на 3+ файла (создать/править/проверить) → число модалок approve, число шагов.
S4 «обрыв загрузки»: kill передачи модели на ~90% → продолжение с места, SHA финала сходится.
S5 «кларификация»: ambiguous-задача → модель спросила (ask_user/Plan-вопрос), а не угадала.
Каждый бенч: шаги воспроизведения + ожидаемое наблюдаемое поведение + число. Если бенч требует живого
движка, а движка нет — пометь BLOCKED_BY_ENV и меряй смежную прокси-метрику (unit/contract), явно указав подмену.

S6 «убийство посреди задачи»: kill worker/sidecar на середине многошаговой задачи → resume с чекпоинта,
без повтора завершённых шагов и с нулём дублированных side-эффектов (идемпотентность §12.4).
S7 «компакция посреди цели»: принудительная компакция/рестарт сессии на середине → цель и активная задача
сохранены дословно (out-of-history metadata §12.2), дрейфа нет.
S8 «смерть движка посреди хода»: падение llama.cpp во время генерации → авто-restart + cooldown + продолжение
или честная ошибка с recover-предложением (не молчаливый hang, не потеря хода).
S9 «длинный код как у Anthropic»: фиче-лист JSON на 5+ пунктов, агент делает по одному за сессию, каждая сессия
начинается с чтения прогресса и заканчивается коммитом + записью; итог — все пункты passing по self-verify.
S10 «обрыв гигантской загрузки»: обрыв скачивания 10+ ГБ модели на ~90% → продолжение с места (Range +
ETag/If-Range, §11.3), финал SHA сходится, сиротских .partial не остаётся.

## 5. ФАЗА A — РАЗБЛОКИРОВКА ПОВСЕДНЕВНОСТИ (P0)

5.1. Очередь вместо busy + message queue (эталоны: Open WebUI, LiteLLM Router).
Gateway: bounded очередь ходов (лимит глубины, честный статус queued/position) вместо мгновенного busy;

Состояния очереди видны (позиция, отмена). Отмена tool.call: провести type:"cancel" через диспетчер до
координатора (сейчас rejected) — зависшие web.fetch/computer_use wait прерываются, не только shutdown.
i18n ru/en симметрично. Тесты: unit на очередь (порядок, лимит, отмена) + компонентный (composer не дизейблит
ввод во время генерации). Метрика: доля убитых busy → 0 на сценарии «двойной клик/двойная отправка».
5.2. Plan/Act + ask_user (эталоны: Cline, Open WebUI v0.11.1).

execute_approved, но без повторных модалок). BUG-8 лечится: отказ/таймаут убивает шаг, не весь ход.
Фронт: переключатель Plan/Act в ChatHeader или Composer, карточка плана с diff-шагами, карточка вопроса.
Тесты: контракт плана (шаги типизированы, digest стабилен), UI-тесты карточек, i18n. Метрика: approve-нагрузка
на типовую многошаговую задачу (цель: −50% модалок при том же числе мутаций).

подмножество, recall зафиксировать числом.
6.6. Персистентность + Memory facts + KV-артефакты (эталоны: Goose Memory/Chat Recall/Todo, Open WebUI artifacts).
task_ledger подключить к чату: рестарт = восстановление истории/очереди/черновиков; факты-память со скоупом
(проект/глобально) с явным UI управления (добавить/удалить, ADR-007: только явным действием); KV-хранилище
артефактов ходов (personal scope; shared — только позже с ACL). Тесты: kill → restore побайтово; факты не

6.7. Token/время-логирование + дневные квоты (эталоны: LiteLLM budgets/spend, Open WebUI analytics).

## 7. ФАЗА C — РЕЖИМЫ, РЕЦЕПТЫ, СЕРВЕР (P2)

7.1. Режимы Ask/Architect/Debug + per-tool Always/Ask/Never поверх TOML (эталоны: §1.2, Roo modes, Goose permissions).

анализ ошибок + трассировка поверх кодинг-контура. i18n, тесты на «override не может разрешить то, что
TOML запрещает».
7.2. Recipes YAML + validate-гейт + /recipe из сессии + cron (эталон: Goose recipes один в один).
Формат: title/description/instructions/prompt/activities/extensions/parameters/retry(response schema)/

Планировщик cron (background/foreground) поверх очереди §5.1; scheduled = только pre-approved recipe +
digest; max_turns против runaway. UI: библиотека рецептов, параметры формой, история запусков. Тесты:
валидатор (позитив/негатив), планировщик (мок времени), sub_recipes параллельно/последовательно.
7.3. ApprovalCard edit-args + липкие решения (эталоны: LM Studio, Open WebUI Tool Permissions).
Правка аргументов перед approve = новый digest = новый approve (инвариант цел); «всегда разрешать этот
инструмент с такими параметрами» → доверенный профиль (§7.1) с управлением в Settings. Тесты: digest
меняется при правке (негатив на подмену), липкое решение скоупится (tool+args-hash, не «всё подряд»).
7.4. Сервер-режим по формуле LM Studio/Jan.
Loopback default; opt-in LAN только с токеном, выданным в момент открытия; capabilities-массив в /v1/models
(tool_use и др.); load/unload/download по API; idle-TTL eviction; живые логи запросов; request timeout для
слабого железа; CORS-переключатель; server-side tool execution — opt-in и только через approval-периметр.
Тесты: бинд наружу без токена невозможен (негатив), capabilities честны (негатив: заявлено — работает).
Документация API — OpenAPI-файл в репо.
7.5. Профили моделей (Modelfile-лайт) + версионирование рантаймов (Engine Protocol-лайт).
Файл-профиль: база + system + параметры + шаблон чата + tool-формат + ожидаемые SHA; per-model kwargs
шаблонов; рантаймы CPU/Vulkan — независимо версионируемые бандлы с SHA-пином и проверкой обновлений.
Параллельные tool_calls в одном ходе + structured outputs для внутренних контрактов (парсинг calls,
классификации) — прокинуть response_format движка, temperature 0 для контрактных вызовов.

## 11. СТОЛП 1 — РАНТАЙМ ОТЛИЧНО: МОДЕЛИ ГРУЗЯТСЯ И РАБОТАЮТ (приоритет = фаза A–B)

Исследование (09.2026): llama.cpp docs + server README, гайды InferenceRig/CraftRigs/poctoprod/Local AI Ops,
GGUF-квант-гиды (AIFoss, Oflight, CanItRun, llmconfigurator), HF issue #4060 + PR #4143 (resume-надёжность),
eval jdhodges 13 локальных моделей (Qwen3.5 4B — 97.5% tool-call), Docker F1-замер (Qwen3 8B/14B топ),
BFCL V4 (single-turn силён, memory/multi-step — открытая проблема у всех). Вывод для LocalComet: побеждает
не «больше модель», а связка «правильный квант + правильные флаги + проверенный tool-формат».

11.1. Аппаратно-адаптивные профили запуска (заменить «нищенские дефолты» и ручной подбор).
Правила из гайдов (проверены бенчами llama-bench, verified на b5000+):
(a) `-ngl 99` сначала (все слои в VRAM), снижать по 4–5 слоёв только при OOM; частичный оффлоад нелинеен
(10% слоёв на CPU = −40–50% скорости) — UI обязан предупреждать о «утёсе», а не молча тормозить;
(b) контекст по задаче, а не максимум: чат 4–8K, документы 16–32K; каждые +8K контекста ≈ +1 ГБ KV (FP16, 8B);
(c) `--flash-attn on` везде где CUDA 7.0+/ROCm (экономия KV 20–50%, бесплатно); (d) KV-квант q8_0 для длинного
контекста; (e) threads = физические ядра (не hyperthreading) для CPU-слоёв, 4–8 при полном GPU-оффлоаде;
(f) batch `-b` вверх (1024–4096 при 16+ ГБ VRAM) для префилла документов — прирост pp до +35–40%;
(g) `--mlock` против своп-джиттера, `--warmup` против сюрприза первого запроса, `--metrics`+`/slots` как
честный источник UI-статусов (NA-012: self-report не авторитет); (h) `--parallel`/continuous batching под
очередь §5.1; `--cache-prompt` для повторяющихся префиксов (system+RAG); `--kv-unified` при OOM на 32K+.
Реализация: тиры железа в адаптивном харнесе (d24d80e уже знает RAM/ядра — добавить VRAM-зонд и spec-тир):
профиль = {ngl-стратегия, ctx, flash-attn, kv-type, threads, batch, parallel} + автодеградация с объяснением
(«влезло 28/32 слоя → −X% скорости, вариант: Qwen3-8B Q4 вместо 14B»). Каждый старт пишет профиль + замеры
в evidence. Тесты: матрица тиров (мок VRAM) → ожидаемый профиль; OOM-симуляция → деградация с бейджем, не hang.
11.2. Советник квантов (Q4_K_M дефолт — но не догма).
Вшитая таблица (bpw, файл/VRAM на 8B, потери): Q8_0 ~8.5bpw/near-lossless/−29% gen-скорости; Q6_K ~6.56/
практически lossless; Q5_K_M ~5.7/+0.06 perplexity — апгрейд для кода и structured output (Q4 шумит именами/
JSON); Q4_K_M ~4.89/+0.18 — дефолт; ниже Q4 — только большие модели и imatrix-IQ. Формула fit:
params×bpw/8 + KV(контекст) + 500 МБ запас; правило «большая модель в Q4 бьёт меньшую в Q8 при том же VRAM»;
«код/математика → на уровень выше». UI: карточка модели показывает «почему этот файл» + альтернативы
(«влезет Q5_K_M 13B вместо Q8_0 8B — лучше почти всегда»). Каталог (INV-CATALOG-001) расширить полями
quant-options + recommended-by-vram. Тест: фит-калькулятор на таблице тиров.
11.3. Загрузка как у взрослых (HF-урок #4060/PR #4143).
Range-resume + sidecar-метаданные (.etag/.size/.url) + `If-Range` + проверка `Content-Range` + `416` →
чистый рестарт; partial именовать по artifact_id (чинит dead-code resume из аудита); прогресс байты/скорость/
ETA + пауза/продолжить через рестарт приложения; сиротские .partial чистить (sweep с владением по имени);
финал: size + SHA-256 + GGUF-magic (уже есть — не сломать). UX: «обрыв на 90% = продолжить», а не «качать с нуля».
Тесты: kill на 41.9%/90% → resume шлёт `Range: bytes=N-`, докачка только хвоста, SHA сходится, сирот нет;
подмена ETag → безопасный рестарт, не склейка чужого хвоста (негатив на silent corruption).
11.4. Tool-call self-test модели на НАШЕМ сервере (главный урок eval-2026).
Шаблонная совместимость важнее размера: топы падали до 15–42% через чужой сервер при живых способностях
(Hammer/xLAM/Mistral Small — понимали задачу, но не могли эмитить формат). Значит: каждая модель каталога
проходит локальный tool-call self-test (selection/args/multi-turn/refusal/format, ~40 кейсов по образцу
jdhodges, temperature 0, seed 42) именно через наш llama.cpp endpoint; бейдж «tool_use: verified/unverified»
в /v1/models-capabilities (§7.4) и в UI; unverified-модели — только чат, агентный контур их не берёт.
Плюс надёжность парсинга: grammar-constrained декодинг (GBNF/response_format движка) для контрактных вызовов
(−85% невалидного JSON), затем СЕМАНТИЧЕСКАЯ валидация (required/enum/типы — valid JSON ≠ valid call) и ретрай
с более строгим промптом с примерами. Тесты: мутированные JSON/аргументы → reject + ретрай-успех; счёт
self-test хранится в evidence и инвалидируется сменой endpoint/шаблона.
11.5. First-run wizard «за 5 минут в чат» (Jan QuickStart-опыт).
Авто-зонд железа → рекомендация «модель+квант+профиль» с объяснением в двух строках → одна кнопка скачать/
запустить → живой чат. Дефолтная модель предзагружается (как foundation у Jan). Провал любого шага — честная
ошибка с действием, не пустой экран. Тест: wizard-state-machine unit + i18n.

## 12. СТОЛП 2 — ДЛИТЕЛЬНЫЕ АГЕНТНЫЕ ДЕЙСТВИЯ (часы, а не ходы)

Исследование (09.2026): Anthropic «Effective harnesses for long-running agents» (initializer + coding agent,
progress-файлы, feature-list JSON, one-feature-at-a-time, clean state, git-коммиты); dreaming.press (две оси:
«поглупение» = context management vs «смерть» = durability, 29%→39% от editing+memory); Veso Memory (METR
time-horizons: 50%-успех 59 мин vs 80%-успех 15 мин у Sonnet 3.7 — вывод: декомпозиция, не марафон; пороги
компакции 50/70/80%; цель ВНЕ истории — out-of-history metadata; иерархические summary-деревья, не линейные);
Zylos checkpointing (Temporal durable execution, idempotency keys, continue-as-new, thread_id как ключ);
Edge-of-Context runtime (session/harness/sandbox/checkpoint/trace, git-branch на запуск, PROGRESS.md);
Matryoshka Agent (Orchestrator с компактным состоянием + fresh Sub-Agents + structured summaries+scores;
Qwen3-4B как оркестратор ≈ o4-mini); any-subagents/OMS/ArgusAgent (сессии→группы→задачи, durable SQLite,
result.json-контракт, изоляция worktree, Manager/Planner/Engineer/Reviewer); supervisor-паттерн (depth ≤3,
таймауты 30с, circuit breaker, stateless supervisor). Доктрина LocalComet: ОБЕ ОСИ ОБЯЗАТЕЛЬНЫ.

12.1. Ось «не поглупеть» (context management): эвикция refetchable tool-результатов (~100k-порог), компакция
в summary-ДЕРЕВО (линейная «суммаризация суммарного» запрещена — информация тает за 3 прохода), memory-файл
фактов вне окна; чекпоинт-суммаризации завершённых подзадач (inputs/outputs/decisions/artifacts), полный трейс
отбрасывается. Пороги 50/70/80% из Veso — в GatewayLimits как константы с именами.
12.2. Цель вне истории (критический паттерн): goal_state/active_task/user_constraints живут в session metadata
и ре-инжектятся в system prompt каждый ход; компактор их никогда не видит (нанобот /goal-образец). Иначе цель
стирается к ~40-му ходу и агент дрейфует незаметно. Тест: 3 принудительные компакции → цель дословно та же.
12.3. Ось «не умереть» (durability): чекпоинт на границе super-step (состояние графа + workspace diff + SHA
коммита + ссылки на артефакты, НЕ сами байты) в durable store (SQLite рядом с task_ledger, не память);
resume = wake(sessionId) → getSession → продолжить с последнего good-step; шаг, упавший mid-flight, НЕ
переисполняет внешние записи дважды (см. 12.4). Kill-тест S6 — обязательный гейт фазы.
12.4. Идемпотентность записей: каждый внешний write несёт ключ workflow_id+step_id; повторное исполнение с тем
же ключом = возврат записанного результата, не повтор side-эффекта. Read-инструменты — replay свободно.
Негативный тест: resume дважды → один тикет/файл/запись (счётчик попыток = 1 в evidence).
12.5. Иерархия Orchestrator → Sub-Agents (Matryoshka-лайт поверх compound task):
оркестратор держит только score-аннотированную историю попыток (что пробовали, счёт, диагностика), сабагенты
стартуют с fresh-контекста (инструкция + выбранные референсы, не вся история); возврат — structured summary +
score; бюджет отладки на попытку; итог — лучшая попытка. Глубина делегирования ≤3, таймаут сабагента 30с,
circuit breaker после N провалов. Тест: оркестратор-контекст не растёт с числом попыток (assert на размер).
12.6. Anthropic-ритуал сессии (процесс, не код): initializer создаёт init.sh + progress-файл + feature-list JSON
+ начальный коммит; каждая coding-сессия: прочитать прогресс+git log → прогнать базовый E2E-тест ПЕРЕД новой
фичей (ловит «сломанное наследство») → одна фича → self-verify тестами → коммит + запись прогресса; запрет
маркировать passing без тестов — в системном промпте строгой формулировкой. Feature-list — JSON со статусами
(модель реже портит JSON, чем Markdown). S9 — приёмка.
12.7. Soft resume + манифест файлов + refresh кредов (межсессионная память): чекпоинт хранит хэши референсных
файлов; при resume — diff и показ пользователю «3 файла изменились, пока вас не было»; при долгой паузе —
soft resume (сводка как свежий контекст, не replay всей истории); креды обновлять ДО первого вызова после
паузы, не после первого 401. Продолжение истории (continue-as-new): при раздутии истории — атомарно новый
запуск с тем же workflow ID и только существенным состоянием.
12.8. Видимость долгого (UX): живой прогресс (фаза/шаг/попытка N, токены/время/последний чекпоинт), heartbeat
«агент жив, последняя активность Xs назад», кнопки Pause/Resume/Cancel (Cancel — через починенный §5.1
type:"cancel"), журнал попыток со score. Пауза = персист + остановка без потери (human-in-the-loop как
частный случай durability: interrupt → persist → resume с вводом). Дедлайны/бюджеты на задачу (время, ходы,
токены) с честным «бюджет исчерпан» вместо тихого умирания.
12.9. Разделение ролей при ревью (Argus-лайт): исполнитель ≠ проверяющий; каждые N шагов или перед финалом —
Reviewer-проход (другая системная роль/профиль) с вердиктом и списком несоответствий; Notion-приёмка проекта
уже так работает — распространить внутрь продукта.
